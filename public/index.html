mac-bootstrap

Bootstrap a machine for remote access

One setup on your Mac. One command per machine. Mac or Linux.

curl -fsSL "<your-site>/install.sh" | bash

First time? Set up your Mac once. Dry run: step 2.

Commands below are built from this page's address.

1. Once, on your Mac

Do this one time. Your Mac then hands each new machine its credentials.

In the browser

In the Tailscale admin console, open Access controls and add tagOwners for tag:bootstrap and a grant to TCP 22 (snippet below). Then open Settings › OAuth clients (newer consoles: Trust credentials) and create an OAuth client with only the Auth Keys (write) scope and the tag tag:bootstrap. Copy its secret.

In Terminal

Paste the secret at the hidden prompt. It goes into your Keychain, and the mac-bootstrap helper is installed.

curl -fsSL "<your-site>/install.sh" | bash -s -- --client-setup --origin "<your-site>"

GitHub token: the hand-off copies your Mac's existing gh login (gh auth token) to the new machine. Broad scopes, shared by both; revoking it logs your Mac out too. On Linux it sits in a plaintext, owner-only file.

Tailnet policy snippet (tag and TCP 22 grant)

Paste into the policy file in the admin console. It uses OpenSSH on TCP 22, not Tailscale SSH.

{
  "tagOwners": { "tag:bootstrap": ["autogroup:admin"] },
  "grants": [{ "src": ["autogroup:member"], "dst": ["tag:bootstrap"], "ip": ["tcp:22"] }]
}
What gets stored, and how to revoke

The OAuth secret stays in your Mac's login Keychain and never leaves it; each hand-off mints a single-use, tagged, preauthorized Tailscale key valid for 1 hour. To rotate the secret, delete and recreate the OAuth client in the admin console and rerun the setup command. To revoke the shared GitHub token run gh auth logout, or revoke the OAuth app authorization at github.com/settings/applications, then gh auth login again on your Mac. Revoking a minted key (Settings, Keys) does not remove a machine already registered; remove it in the admin console.

2. On each new machine

macOS, Ubuntu, Debian, Fedora, RHEL or Arch. No browser opens on it.

  1. Mac only: the script opens System Settings › Sharing. Turn on Remote Login (Screen Sharing is optional, by hand).
  2. Run the command below on the new machine and type the sudo password.
  3. On your Mac, run the printed mac-bootstrap handoff user@IP, check the fingerprint matches the new machine's screen, and type its password.
  4. Done: it joins your tailnet, logs gh in and sets your git identity.

The command (run it on the new machine):

curl -fsSL "<your-site>/install.sh" | bash

Dry run first. Prints what it would do and changes nothing:

curl -fsSL "<your-site>/install.sh" | bash -s -- --dry-run
Mac only: turn on Remote Login (click path)

On macOS Tahoe 26 and Sequoia 15 the script opens this pane for you if Remote Login is off. You need an administrator account.

System Settings›General›Sharing
  1. Turn on Remote Login, then click the ⓘ button next to it.
  2. Allow access for: Only these users with your account, or All users.
  3. Allow full disk access for remote users: leave off unless an SSH session genuinely needs it.

Source: Apple Support: Allow a remote computer to access your Mac. Apple notes that enabling Remote Login reduces your Mac's security.

Screen Sharing (optional)

Same pane: turn on Screen Sharing, choose Only these users, and leave VNC viewers may control screen with password off. Source: Apple Support: Turn Screen Sharing on or off on Mac.

Check they are on (no sudo)

nc -z localhost 22 && echo "Remote Login: listening"
nc -z localhost 5900 && echo "Screen Sharing: listening"

Each line prints only when the port accepts a connection (22 = SSH, 5900 = Screen Sharing). No output means that switch is off.

No SSH login? Paste a bundle instead

On your Mac run this, press p on the new machine's wait screen, and paste at the hidden prompt. The bundle contains your GitHub token, and --copy puts it on your clipboard.

mac-bootstrap bundle --copy
Can login be non-interactive?

Yes: that is the hand-off in the list above. Your Mac sends the new machine a single-use tskey-auth- key over SSH and the script passes it to tailscale up as --auth-key=file:/path, never on a command line. No browser opens on the new machine.

Advanced: pass your own keys without leaking them

Skips the hand-off for what you supply. Run these four commands one at a time (pasting them together would feed the later lines to the hidden prompts). Press Enter on a prompt to skip that secret. A tskey-client- (OAuth) value in TS_AUTHKEY also needs TS_TAGS, for example TS_TAGS=tag:bootstrap placed before bash.

  1. hidden read
  2. shell variables, not exported
  3. bash only, never curl
  4. unset
read -rs "TS_AUTHKEY?Tailscale auth key: "; echo
read -rs "GH_TOKEN?GitHub token: "; echo
curl -fsSL "<your-site>/install.sh" | TS_AUTHKEY="$TS_AUTHKEY" GH_TOKEN="$GH_TOKEN" bash
unset TS_AUTHKEY GH_TOKEN

Why this shape: the hidden read keeps the secret out of your shell history and out of any command line (ps shows arguments, not variables); the variables are not exported, so only bash receives them, never curl. The script then removes them from its own environment before running anything else. This page never asks for a secret itself.

Order of steps and sudo

The script runs: preflight, packages (Homebrew on a Mac, your distro's package manager on Linux), Tailscale, the wait for the hand-off, git and gh, git identity, summary. You may be asked for your password more than once (sudo), for example to start the daemon.

macOS notes (Homebrew tailscale formula)
  • This is the open-source tailscaled + CLI, not the Tailscale app. It must not coexist with /Applications/Tailscale.app or the tailscale-app cask; the script stops if it finds either. Variant differences: Tailscale on macOS variants.
  • tailscaled needs root on macOS, so the script starts it with sudo brew services start tailscale; expect a password prompt (possibly more than one).
  • If Tailscale is already Running, the script skips login and does not spend your key; with TS_HOSTNAME set it only renames the machine.

Full write-up with source links: docs/tailscale-auth-key.md in the repository.

3. Optional: iTerm2 (both Macs)

iTerm2 shows a hostname badge and switches profile when you SSH. It needs shell integration on every participating Mac.

On the bootstrapped Mac

Re-run the install command with shell integration:

curl -fsSL "<your-site>/install.sh" | bash -s -- --iterm2-shell-integration

On the client Mac (the one you SSH from)

Replace my-mac with the short hostname that install.sh prints in its final summary.

curl -fsSL "<your-site>/iterm2-client.sh" | bash -s -- --host my-mac --shell-integration
Why both Macs need it

When you SSH from one Mac to the other, iTerm2 can show a hostname badge and switch profile automatically. This needs iTerm2 shell integration on every participating Mac: the remote reports its hostname to iTerm2, and the client needs it too so iTerm2 switches back to the original profile after the SSH session ends.

Client command details and a different SSH user

Replace my-mac with the short hostname that install.sh prints in its final summary on the bootstrapped Mac (see below). --shell-integration installs iTerm2 shell integration on the client as well.

If your SSH user differs from your client user, add --user <ssh-user>:

curl -fsSL "<your-site>/iterm2-client.sh" | bash -s -- --host my-mac --user your-ssh-user --shell-integration
Client options

Which name for --host

Use the short hostname (hostname -s) that install.sh prints in its final summary on the bootstrapped Mac, including its ready-made client command. iTerm2's shell integration reports the remote's hostname -f, usually <that-name>.local, and the profile rules match <host>.*, so the short name matches both .local and *.ts.net names. --host is not the Tailscale/MagicDNS name and not TS_HOSTNAME.

If you no longer have the summary, scutil --get LocalHostName on that Mac is usually the same value, but it can differ when macOS HostName is set or DHCP supplies a name; prefer the printed value.

This writes one Dynamic Profile, mac-bootstrap-<host>.json, into the profiles directory. What to expect: when a session SSHes into that host, iTerm2 switches to the profile automatically and shows the badge, and switches back when the SSH session ends.

Done

Check tailscale status on the new machine, then connect from your client with ssh <user>@<tailscale-hostname> or Screen Sharing to vnc://<tailscale-hostname>.

The scripts are served as plain text: open <your-site>/install.sh to read exactly what you will run before running it.
